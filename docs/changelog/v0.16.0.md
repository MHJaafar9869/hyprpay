CyberSource gains the operational surface around a payment rather than more of the payment itself: BIN lookup so a card can be identified before it is charged, full webhook subscription management so notifications can be onboarded without the Business Center, and the corrections that were previously unreachable — voiding an independently-made capture, undoing a refund or a credit, and reversing a request whose reply never arrived.

### Added
- **BIN lookup** — `lookupBin()` (`POST /bin/v1/binlookup`) answers what a card *is* before authorizing: brand, funding source, issuer country, platform, card product, and capability flags. That timing is the point — routing, surcharging, card-type offers, whether to offer installments, and whether 3-D Secure is supported are all pre-charge decisions. Accepts a raw PAN or, preferably, a transient token or vault reference, so no card data need leave the vault. `BinLookupResult::isResolved()` is deliberately strict: `MULTIPLE` and `NO MATCH` leave the attributes untrustworthy, and "unknown card" is never grounds for refusing a payment.
- **`CybersourceCardNetwork` resolution** — `fromCyberSourceCode()`, `fromBrandName()`, and `resolve()`, plus `network()` on `BinLookupResult`, `PaymentInstrument`, and `OrchestratedPaymentResult`. The card brand previously reached the SDK in three shapes depending on origin — a numeric code from BIN lookup and the vault, a lowercase name from a verified orchestrated result, an uppercase name from BIN lookup's brand field — with the code-to-name map private to one trait and nothing mapping to the enum that already existed. Branching on the card network is now one `match`, whatever the source.
- **Webhook subscription management** — `createWebhook`, `listWebhooks`, `getWebhook`, `updateWebhook`, `setWebhookStatus`, `deleteWebhook`, `testWebhook`, `listWebhookProducts`, and `createWebhookSecurityKey`. The SDK could verify an inbound webhook but not manage the subscription that sends it. `createWebhookSecurityKey()` is the pivotal one: the key it returns is the value the `webhook_secret` credential holds, and the one `verifyWebhook()` checks signatures against — it is shown once and cannot be read back, and it must exist *before* the subscription, because the gateway signs every notification with it.
- **`WebhookProductCatalog` / `WebhookEventType`** — the subscribable catalogue, typed. Product ids and event names are entitlement-scoped and events are nested per product, so neither is an enum; instead the catalogue surfaces `eventNames()`, `toSubscription()`, and the per-event `timeSensitivity` and `payloadEncryption` flags that decide how a subscription should be configured.
- **Corrections that were previously unreachable** — `voidCapture`, `refundCapture`, `voidCredit`, and `voidRefund`. CyberSource scopes these by resource: `/pts/v2/payments/{id}/voids` is documented as being for authorization and capture requested *together*, so once you capture separately the capture is its own resource and the payment path cannot reach it. Refunding or voiding a capture, and voiding a refund or a credit, were simply impossible before.
- **`timeoutVoid()` and `timeoutReversal()`** — cancel a payment, capture, refund, or credit whose reply never arrived. They take no resource id, because the response that would have carried one never came; they match on the merchant transaction id from the original request instead. Complements reconciling by reference rather than replacing it: `findSuccessfulTransactionByReference()` tells you *whether* a lost request settled and is eventually consistent, while a timeout void *undoes* it and acts immediately. Without a timeout reversal a timed-out authorization strands a hold until the issuer expires it.
- **`incrementAuthorization()`** — raises the amount already authorized, keeping one hold, for hotels and rentals where the final bill is unknown when the card is presented. Authorizing again instead places a second hold and withholds the funds twice. The request carries the amount to *add*, not the new total.
- **`creditPayment()`** — pushes money to a card with no original transaction behind it. Distinct from a refund, which returns part of a specific captured payment and is bounded by it; a credit has no amount cap and no sale to tie it to, which is why processors watch them and why it belongs behind payout-grade authorisation.
- **`refreshPaymentStatus()`** — asks CyberSource to re-check a payment with the processor, for the alternative payment methods that settle asynchronously. Unlike `getTransaction()`, which reads CyberSource's own record.
- **`BinLookupStatus`, `CardFundingSource`, `CardPlatform`, `WebhookStatus`, `WebhookSecurityType`, `WebhookRetryAlgorithm` enums**, and the `BinLookupRequest`, `CreateWebhookRequest`, `UpdateWebhookRequest`, `IncrementAuthorizationRequest`, `CreditRequest`, and `TimeoutVoidRequest` DTOs.

### Changed
- **`ChargeRequest`, `CaptureRequest`, and `RefundRequest` gain `$merchantTransactionId`.** It is emitted as `clientReferenceInformation.transactionId`, and it is the precondition for a later timeout void or reversal — CyberSource matches on it, and it cannot be supplied retrospectively. Set it on anything you may need to undo blind. Additive and optional; existing calls are unchanged.
- **`ClientReference::block()`** replaces the bare `code()` call in the payment, capture, and refund payload builders, so the correlation code and the merchant transaction id are emitted together.
- **Docs: the action tree is reorganised around the integration journey.** Groups now run Checkout → Before charging → Fraud screening → 3-D Secure → Charging → Corrections → After the payment, with webhooks given their own group and one section per operation, and cross-cutting concerns moved to the end. "Payment flow" previously covered four unrelated jobs — getting a credential, deciding, charging, and handling refusal — so its name predicted nothing.
