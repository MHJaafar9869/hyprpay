CyberSource grows a full recurring-billing stack and the operational surface around it: subscriptions and the plans they are built from, a complete vault token lifecycle, Account Updater to keep those stored cards alive, report management on demand or on a schedule, and the Visa Bank Account Validation Service for pre-ACH checks. Between them they close the two gaps that previously made a stored credential a dead end — you can now read, re-date, and delete a vaulted card, and let the card networks refresh it before a rebill fails.

### Added
- **CyberSource Recurring Billing subscriptions** — `createSubscription`, `updateSubscription`, `getSubscription`, `listSubscriptions`, `suspendSubscription`, `activateSubscription`, and `cancelSubscription` on `CybersourceUnifiedCheckoutGateway` drive a billing schedule CyberSource runs itself (`/rbs/v1/subscriptions`), as opposed to `chargeStoredCredential`, where your own scheduler raises each charge. A subscription enrols an already-vaulted TMS customer — it carries no card data and charges nothing at create time; the first charge falls on the request's start date. The cadence comes from a `planId`, from an inline `billingPeriod`/`billingCycles`, or from both with the inline values overriding the plan. Suspending is reversible via `activateSubscription` (whose `processMissedPayments` flag is sent in the signed request target); cancelling is terminal. Like `confirmOrchestratedPayment` and `createMicroformSession`, these sit outside `PaymentGatewayInterface`.
- **`updateSubscription` (PATCH) and `listSubscriptions`** — amend a live subscription in place, and page through the subscription book (CyberSource's `getAllSubscriptions`). The update is partial: only the fields set are sent, and CyberSource's schema is narrower than a create's — the cycle count and amounts can change, but the billing period and currency cannot, so a `Money` passed here contributes its amount while its currency is ignored. An update can return `PENDING_REVIEW` (accepted but held rather than applied), reported as `success: true` with the raw verdict preserved on `$requestStatus`.
- **`CreateSubscriptionRequest` / `UpdateSubscriptionRequest` / `ListSubscriptionsRequest` / `SubscriptionResult` / `SubscriptionPage`** — the subscription input and output DTOs. `ListSubscriptionsRequest::nextPage()` and `SubscriptionPage::hasMore()`/`count()`/`isEmpty()` page a filtered list without recomputing offsets by hand; `SubscriptionPage::$totalCount` spans the whole filtered set, not the page. `SubscriptionResult` keeps the two CyberSource statuses apart: `$status` is the subscription's own normalised lifecycle state and `$requestStatus` the raw verdict on the call itself, so a create that returns `COMPLETED` with a still-`Pending` subscription is not mistaken for a finished one.
- **`SubscriptionStatus` enum** — the normalised subscription lifecycle (`Pending`, `Active`, `Suspended`, `Delinquent`, `Cancelled`, `Completed`, `Failed`) with `label()`, `isBilling()`, and `isTerminal()`. CyberSource's raw states map onto it through the new `CybersourceSubscriptionStatus`.
- **`BillingPeriod` value object and `BillingPeriodUnit` enum** — a typed billing cadence (`BillingPeriod::monthly()`, `::monthly(3)`, `::weekly()`, `::daily(7)`, `::yearly()`) replacing free-form length/unit strings, validated to at least one unit.
- **`CybersourceCommerceIndicator` enum** — `RECURRING` / `INTERNET` / `MOTO` for a subscription's `processingInformation.commerceIndicator`, typed rather than stringly.
- **CyberSource vault token lifecycle** — `getPaymentInstrument`, `listPaymentInstruments`, `updatePaymentInstrument`, `deletePaymentInstrument`, `getCustomer`, `deleteCustomer`, and `deleteInstrumentIdentifier` complete the TMS story `vaultInstrument` began: until now the SDK could create tokens but never read, amend, or remove them. Reading a stored instrument back catches a dead card *at rest* — `PaymentInstrument::isExpired()` and `PaymentInstrumentState::isChargeable()` answer without a network call — instead of at charge time, and `updatePaymentInstrument` re-dates a reissued card so every subscription and stored-credential charge already pointing at it keeps working with no re-collection. The card number stays immutable (it belongs to the instrument identifier), a customer's default instrument cannot be deleted while they hold others, and `listPaymentInstruments` returns a paged `PaymentInstrumentPage` with `hasMore()`/`default()`.
- **CyberSource recurring billing plans** — `createPlan`, `getPlan`, `listPlans`, `updatePlan`, `activatePlan`, `deactivatePlan`, `deletePlan`, and `generatePlanCode` manage the reusable template `CreateSubscriptionRequest::$planId` references, which previously had to be built by hand in the Business Center. `PlanStatus` (DRAFT/ACTIVE/INACTIVE) gates subscribability via `PlanResult::isSubscribable()`. Note the asymmetry: **`updatePlan` can change the billing period, `updateSubscription` cannot** — a plan is a template, a subscription a live agreement — and a plan change governs subscriptions created afterwards rather than re-pricing those already running. `listSubscriptionPayments` adds the non-webhook route to diagnosing a `DELINQUENT` subscription.
- **CyberSource Account Updater** — `createAccountUpdaterBatch`, `getAccountUpdaterBatchStatus`, `getAccountUpdaterBatchReport`, and `listAccountUpdaterBatches` submit vaulted cards for the card networks to refresh, pushing reissued, re-dated, and closed accounts back into the vault. This is the standing fix for the permanent declines a reissued card otherwise causes: only token ids are sent, never card numbers. Processing is asynchronous, so the create returns a batch id to poll — `AccountUpdaterBatchStatus::isInProgress()`/`isComplete()`/`isFailed()`, then `AccountUpdaterBatch::hasUpdates()` before fetching the report. Amex requires an `AccountUpdaterBatchType::AmexRegistration` batch rather than the `oneOff` one Visa and Mastercard use.
- **Report definition discovery and `ReportDefinitionName`** — `listReportDefinitions` and `getReportDefinition` expose the catalogue behind `CreateReportRequest::$definitionName`, including each definition's selectable fields via `ReportDefinition::fieldNames()`/`requiredFieldNames()`/`supports()`. The 19 reports CyberSource documents as standard are typed as `ReportDefinitionName` (`TransactionRequestClass`, `PaymentBatchDetailClass`, …) with `label()`, `resolve()`, `toValue()`, and `allValues()`; `$definitionName` accepts `ReportDefinitionName|string`, so the enum gives typo-safety without locking out a custom definition a merchant is entitled to. `ReportSubscriptionType` (CUSTOM/STANDARD/CLASSIC) selects which family a name resolves against. Report **fields** are deliberately not enumerated — they are a property of each definition, not of reporting as a whole.
- **CyberSource report management** — `createReport`, `listReports`, `getReport`, and `downloadReport` drive the Reporting service (`/reporting/v3/*`) for reconciliation and settlement files, and `createReportSubscription`, `listReportSubscriptions`, `getReportSubscription`, and `deleteReportSubscription` manage the schedules that generate them recurrently. Generation is asynchronous, so `createReport` returns `bool` (CyberSource answers with an empty 201) and the queued report is located with `listReports`; `ReportStatus` separates the three outcomes that matter — `isInProgress()` means poll, `NO_DATA` is a *successful* run that matched nothing, and only `ERROR` is a failure. Downloads are keyed by report **name and date** — the end of the period covered, in the report's timezone, never the report id — which `Report::downloadRequest()` derives for you.
- **`ReportFormat` / `ReportFrequency` / `ReportStatus` enums** and the `Report`, `ReportFile`, `ReportSubscription`, `CreateReportRequest`, `ListReportsRequest`, `DownloadReportRequest`, and `CreateReportSubscriptionRequest` DTOs. `ReportFrequency::needsStartDay()`/`needsInterval()` decide which schedule fields a cadence carries, so a daily subscription never sends fields CyberSource would reject; `ReportFile` exposes `isEmpty()`, `bytes()`, and `filename()` over the unparsed CSV/XML body.
- **Visa Bank Account Validation (BAVS)** — `validateBankAccount` posts to `/bavs/v1/account-validations` to check a routing/account pair is a real, open account *before* an ACH debit, satisfying Nacha's account-validation mandate for WEB debits. It authorises nothing and moves no money. `BankAccountValidationResult::isValid()` is deliberately strict — only the documented `00` result code passes — and `isInconclusive()` separates "the check could not run" (`-1` unknown error, `-2` service unavailable) from a bad account, so an outage is retried rather than turned into a rejected customer. Accepts raw bank details or a vault customer/instrument token, which keeps the raw numbers in the vault; the operation sits outside `PaymentGatewayInterface`, so the logging decorator never sees them.
- **New `CybersourceClient` verbs** — `postWithoutBody()` (a signed POST for the action endpoints that name their resource entirely in the path, whose digest covers the empty string exactly as CyberSource's own SDKs sign a bodyless POST), `patch()` for partial updates, `put()` for the create-or-replace subscription endpoint, `delete()` (no digest — DELETE carries no body), and `getBody()` for a raw non-JSON response with an `Accept` override, which is how a report file is fetched. A path may now carry a query string, which is signed as part of the request target.

### Changed
- **The CyberSource `Accept` header is now overridable.** It still defaults to `application/hal+json` on every JSON call; a report download overrides it with the report's own MIME type, because that endpoint returns the file itself and asking for the wrong format fails rather than converting. It is not part of the signed header set either way, so no existing request changes.
- **`DeclineClassifier::fromResult()` now accepts a `SubscriptionResult`** as well as a `PaymentResult`. A Recurring Billing create that comes back `DECLINED` carries the same `errorInformation.reason` and `processorInformation.merchantAdvice.code` signals as a declined authorization, so a permanent refusal (re-collect the card) is told apart from a transient one (retry) by the same rules — and `DeclineClassifier::classify()` reads a verified webhook payload directly, which is how a failed rebill that turns a subscription `DELINQUENT` is triaged.
